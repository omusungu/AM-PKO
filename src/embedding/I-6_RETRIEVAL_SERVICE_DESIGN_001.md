# AM-PKO I-6 — RetrievalService Design

Status: DESIGN_RECONCILED
Contract version: 0.2-design

## Purpose

I-6 is the retrieval-orchestration boundary for AM-PKO.

It coordinates a T-5 QueryRequest with query-vector generation and
I-4 EmbeddingStore search, producing an ordered collection of T-6
RankedResult values.

I-6 does not redefine embedding-model behavior, vector storage,
KnowledgeRecord transformation, or evaluation semantics.

## Reconciled flow

The retrieval flow is:

T-5 QueryRequest
→ query embedding path
→ query vector
→ I-4 EmbeddingStore.search()
→ ordered VectorStoreMatch collection
→ ordered T-6 RankedResult collection

Each VectorStoreMatch contains:

- the immutable T-3 VectorRecord;
- the transient retrieval score produced by I-4.

I-6 converts each VectorStoreMatch into a T-6 RankedResult while
preserving record identity, retrieval score, and I-4 ordering.

The query embedding path uses the existing model/runtime boundary
without modifying the frozen I-3 EmbeddingModel contract.

## Responsibilities

I-6 may:

- accept a T-5 QueryRequest;
- obtain a query embedding through an approved query-embedding execution path;
- call I-4 EmbeddingStore.search();
- forward k, filters, and include_excluded semantics;
- consume the ordered VectorStoreMatch collection returned by I-4;
- convert each VectorStoreMatch into a T-6 RankedResult;
- preserve I-4 result ordering;
- preserve the retrieval score generated by I-4.

## Non-responsibilities

I-6 must not:

- redefine I-3 EmbeddingModel;
- generate T-2 EmbeddingDocuments;
- transform KnowledgeRecords;
- generate or mutate VectorRecords;
- implement vector storage;
- implement cosine similarity;
- independently reorder or rescore I-4 results;
- calculate or reinterpret I-4 retrieval scores;
- store retrieval scores in T-4 payload metadata;
- traverse relationship graphs;
- perform graph/vector fusion;
- perform RAG synthesis;
- evaluate retrieval metrics;
- select a production embedding model;
- select a persistent vector database.

## Relationship to frozen boundaries

I-2 remains responsible for deterministic KnowledgeRecord → T-2
EmbeddingDocument generation.

I-3 remains responsible for model-agnostic embedding execution.

I-4 remains responsible for vector storage, similarity computation,
retrieval-score generation, filtering, exclusion handling, deterministic
ordering, top-k selection, and construction of VectorStoreMatch values.

I-5 remains responsible for embedding-service execution over T-2
EmbeddingDocuments.

I-6 is an orchestration boundary above these components and must not
duplicate their responsibilities.

## Query embedding boundary

The frozen I-3 abstract contract exposes:

EmbeddingModel.embed(text)

The llama.cpp adapter additionally exposes query/document-specific
methods, but those adapter methods are not part of the frozen I-3
abstract contract.

I-6 therefore consumes the separately defined QueryEmbedder boundary
rather than modifying I-3.

The current reference query-embedding path is:

I-6 RetrievalService
→ QueryEmbedder
→ LlamaCppQueryEmbedder
→ existing llama.cpp adapter query-embedding capability.

I-6 does not define model-specific prefixes, pooling, normalization,
tokenization, or other model behavior.

## T-5 relationship

T-5 provides:

- query text;
- positive k;
- optional I-4-compatible metadata filters;
- include_excluded behavior.

I-6 consumes these fields but does not alter T-5 semantics.

## I-4 relationship

I-4 search accepts:

- query vector;
- k;
- optional filters;
- include_excluded.

I-4 returns:

list[VectorStoreMatch]

Each match contains:

- match.record: T-3 VectorRecord;
- match.score: transient retrieval score.

I-6 does not recompute, normalize, reinterpret, or independently
rank these scores.

## T-6 relationship

I-6 maps each I-4 VectorStoreMatch as follows:

match.record.identity.record_id
→ RankedResult.record_id

match.score
→ RankedResult.score

The resulting T-6 collection preserves the exact ordering returned by I-4.

I-6 does not perform an additional sort.

## T-4 protection

Retrieval scores are transient query-dependent values.

They are transported through VectorStoreMatch and must not be added to
the T-4 VectorRecord payload.

I-6 must never depend on an undocumented payload field such as
_retrieval_score.

## T-7 relationship

T-7 evaluates retrieval behavior using experiment inputs, judgments,
per-query results, and aggregate metrics.

T-7 is outside the I-6 runtime retrieval path.

I-6 must not calculate Recall, nDCG, MRR, or other evaluation metrics.

## Freeze prerequisites

Before I-6 is frozen, the following must be validated:

1. T-5 QueryRequest acceptance and forwarding;
2. query-embedding delegation;
3. I-4 VectorStoreMatch consumption;
4. record_id preservation;
5. retrieval-score preservation;
6. I-4 ordering preservation;
7. T-6 RankedResult construction;
8. rejection of non-VectorStoreMatch I-4 results;
9. absence of retrieval-score contamination in T-4;
10. absence of similarity recomputation or independent ranking.

## Reconstruction and reconciliation status

The original historical I-6 implementation was not recoverable.

This design was reconstructed from:

- T-5 QueryRequest design;
- T-6 RankedResult design;
- I-4 EmbeddingStore contract;
- I-3 EmbeddingModel contract;
- I-5 EmbeddingService contract;
- EXP-4B5 retrieval behavior;
- existing adapter behavior;
- the approved I-4/T-6 score-transport decision;
- the frozen VectorStoreMatch boundary.

The original reconstruction has now been reconciled with the validated
I-4 v0.2 score-transport boundary and the implemented I-6 RetrievalService.

No frozen I-2, I-3, I-4, or I-5 contract is modified by this document.

I-6 remains NOT_FROZEN pending final conformance validation.
